## 为什么"设计先行"

ImagineOS Alpha 验证的不是功能清单，而是一个心理命题：普通人在两个关键时刻（选定方向、第一次自然语言修订）能否产生"这是我引导出来的"归属感。这类命题无法在代码写完之后靠返补救——屏幕的布局、等待的话术、失败时的措辞、修订的反馈节奏，每一项都直接决定情绪曲线的走向。因此设计在 M3（Phase 11~14）动工之前完成，实现阶段以本包为验收依据：task-tree 中 Epic 7~10 的体验性 AC 条款，以本包 05 号红线清单为准；界面结构与组件以 02/03 号文件为准。

## 设计北极星：两个关键时刻

一切屏幕、模式与红线的存在理由，都可以追溯到这两个时刻——

1. **选定方向**（S3）：用户第一次从"AI 说了算"切换到"我说了算"。方向的真实差异是归属感点燃的前提。
2. **第一次修订**（S6，"再温暖一点"）：用户验证"我能不能指挥它"。这是 ImagineOS 与抽卡式生成器的分水岭。

任何设计决策如果不同时服务这两个时刻与金路径，就不属于 Alpha。

## 设计五原则

1. **对话优先于面板。** 用户面对的是对话、方向与选择，不是工具面板。ImagineOS 拒绝画布/图层/属性检查器范式——那是给设计师的工具；我们的用户只表达、选择、修订。（FigCraft 借鉴评审中明确排除"画布式 UI"的原因。）
2. **用户语言优先。** 界面零术语墙：prompt、model、seed、resolution 等技术词永不裸露给用户（红线 R9）。
3. **永远可回退。** 修订产生 v2，v1 永在；版本时间线常驻可达（红线 R4；数据层由主线基座「快照式版本链 + Provenance」保障，ADR-003 事件溯源为 Stage 2 演进方向）。
4. **期待感优先于秒数。** 生成等待是产品体验而非技术缺陷：分镜逐张点亮、阶段性话术、不承诺精确秒数（模式 4）。
5. **诚实优先于惊艳。** AI 参与必标识（红线 R7）；修订没听懂就说没听懂；失败说人话并给出路（模式 5/6/9）。

## 变更流程

本包批准后即为基线。任何设计变更（token 语义、屏幕结构、红线增删）以"设计变更"提出并升级产品负责人评审，通过后升版本号——与 charter §85 升级纪律一致。实现阶段可以在不跨语义的前提下微调像素值，但不得偏离模式规则与红线。
